# Popolog 실기기 일괄 확인 체크리스트

작성일: 2026-10-31 · 상태: **절차 작성 완료 / 실기기 확인 미실행**

백업·복구와 차량 매각 삭제의 미완료 확인 항목을 한 번에 수행하기 위한 문서다. 기존 Pleos 연동의 미확인 항목도 뒤에 모았다. 체크박스는 절차가 실제로 기대 결과를 만족했을 때만 표시한다. 재현하지 못했거나 장비가 없으면 `미실행` 또는 `환경 제약`으로 기록한다.

## 확인 순서

1. 준비 및 기준 데이터 기록
2. 화면·백업 정상 동작
3. 백업 실패·중단과 잘못된 파일 처리
4. 앱 제거·재설치·복구 및 기록 비교
5. 차량 매각 삭제 취소 → 실패·재시도 → 완료·재실행
6. Pleos 실제 연동 확인(지원 기기에서 별도 수행)
7. 결과표 작성 및 OpenSpec 반영

앱 제거·전체 삭제는 앞 단계의 기준 자료를 확보한 뒤 마지막 순서대로 수행한다. 개인 실사용 기록이 없는 전용 확인 기기·앱 데이터를 사용한다. 문서를 작성한 것만으로 OpenSpec 작업을 완료 처리하지 않는다.

## 기준 데이터와 증거

확인용 데이터에 다음을 포함한다. 데모 예시 데이터도 사용할 수 있지만, 아래에 확인용 표식을 추가해 복구 여부를 구분한다.

- 운행: 출발·도착 좌표가 있는 기록, 운행 목적을 확인한 기록, 확인된 서식 이용자·부서.
- 비용: `실기기확인-기준` 메모가 있는 비용, 정비 비용, 금액과 결제 장소.
- 장소·운전자: 구별 가능한 확인용 이름과 설정값.
- 무결성: 정상 체인과 앵커. 대기·완료 영수증 상태를 구분해 기록한다.
- 연동 대기 항목: 해당 모드에서 제공할 수 있을 때만 준비한다. 실제 연동 소스가 없는 실제 모드에서 임의로 만들지 않는다.
- 내보내기: PDF·CSV·검증 JSON 각 1개 이상을 `Download/Popolog`에 저장한다.
- 보존 대조군: 전용 폴더에 관계없는 `사용자메모.txt`를 만든다. 내보낸 파일의 복사본 1개는 관리 폴더 밖의 별도 확인 폴더에 둔다.

## 2026-11-04 변경: 암호화 형식 반영

앱 DB와 공용 백업이 암호화되고(task 2.1), 매각 삭제 앞에 차량 밖 저장 단계가 생겼다(task 1.3). 이 문서의 B·C는 이 새 형식 기준이다. 아래 에뮬레이터 확인은 별도 시험 패키지(`ai.chagok.encverify*`)에서 했으며, 실기기·실제 문서 선택기 확인은 모두 남아 있다.

- **백업 파일 형식:** `format=popolog-backup-enc` 봉투. 머리말에 `createdAt`·`demo`·내보내기 파일 목록(`files`/`folders`)이 평문이고, 운행·비용·좌표·원장은 암호문(`data`)이다. 데이터 키(AES-256-GCM)를 PIN 유도 키와 복구 코드 유도 키(PBKDF2-SHA256 210,000회)로 각각 감싼 `wraps` 2개가 들어 있다. `.done`은 파일 전체 SHA-256이다.
- **선행 조건:** 백업을 만들려면 관리자 PIN이 설정(또는 업데이트 후 1회 인증)되어 있어야 한다. 설정 직후 복구 코드를 적어 둔다(화면 캡처 불가).
- **재설치 후 복구:** 새 PIN을 정해도 옛 백업은 이 기기 키로 열리지 않는다. 복구 때 **백업을 만들 때의 PIN 또는 복구 코드**를 입력해야 한다.
- **JSON 손편집 변형:** 기록 본문이 암호문이라 payload를 손으로 고쳐 체크섬을 다시 맞추는 방식은 쓸 수 없다. 봉투 머리말·`.done`만 편집하는 변형은 가능하다.

## A. 화면과 정상 백업

### A1. 첫 실행·화면·폴더 선택

- [ ] **절차:** 설정을 열고 넓은·좁은 창 또는 가로·세로 화면에서 확인한다. 백업 폴더 설정을 누르고 한 번은 취소한 뒤, 다시 열어 폴더 A를 선택한다.
- **기대:** 제목·상태·실제 운행/비용 건수가 읽히고 버튼·본문이 겹치거나 잘리지 않는다. 취소 시 현재 데이터가 유지된다. 성공 전에는 백업 완료로 표시하지 않는다. 로컬 폴더 접근을 허용한 뒤 최초 백업이 시작된다.
- **증거:** 설정 화면, 선택한 폴더 경로, 첫 완료 시각, `.json`/`.done` 파일 목록.

### A2. 최초 백업·변경 반영·재실행

- [ ] **절차:** 최초 백업 완료를 기다린다. 비용 1건의 금액·메모를 바꾸고 저장한다. 자동 백업 완료 후 앱을 정상 종료·재실행한다. 수동 `지금 백업하기`도 한 번 누른다.
- **기대:** 마지막 완료 시각이 갱신된다. 최신 백업에 변경된 값이 들어간다. 재실행 후 폴더 접근이 유지된다. 파일 쌍은 성공한 최신·직전 세대가 남고 계속 무한히 늘지 않는다. 기록 무결성이 정상이다.
- **증거:** 변경 전후 비용, 백업 파일 이름·시각·개수, 무결성 화면.

### A3. 폴더 변경 이력

- [ ] **절차:** 폴더 A의 정상 백업을 남긴 상태에서 `백업 폴더 변경`으로 B를 선택하고 새 백업을 완료한다.
- **기대:** 새 백업은 B에 생긴다. A의 사본도 이후 매각 삭제 대상에서 누락되지 않는다. 이 항목의 최종 삭제 여부는 C4에서 함께 확인한다.
- **증거:** A·B 경로와 파일 목록. 이후 다른 확인을 위해 두 폴더를 이동·삭제하지 않는다.

## B. 실패 처리와 재설치 복구

### B1. 접근·저장 실패와 재시도

- [ ] **절차:** 정상 백업 사본을 확보한다. 기기가 제공하는 방법으로 해당 폴더의 문서 접근을 철회하거나, 전용 이동식 저장소를 분리하는 등 쓰기가 실제로 실패하는 조건을 만든다. 비용을 수정하고 백업을 시도한다. 접근을 다시 허용하고 재시도한다.
- **기대:** 실패를 완료로 표시하지 않는다. 마지막 정상 백업과 완료 시각이 보존되고 최신 변경은 미반영으로 구분된다. 재승인·재시도 후 최신 변경이 반영된다.
- **증거:** 실패 조건, 오류 화면, 남은 정상 파일, 재시도 성공 화면.
- **조건:** 권한 철회·분리 기능이 없으면 `환경 제약`으로 기록한다. 단순 파일 선택 취소를 쓰기 실패 검증으로 대체하지 않는다. 공간 부족도 전용 확인 저장소에서 재현할 수 있을 때 같은 기대 결과로 확인한다.

### B2. 백업 도중 중단

- [ ] **절차:** 정상 세대 1개를 확보한다. 새 백업의 작업 중 상태에서 OS의 앱 강제 종료로 프로세스를 중단하고 재실행한다. 짧은 작업이라 중간 시점을 잡지 못했다면 재현하지 못했다고 기록한다.
- **기대:** 이전 완료 세대가 읽힌다. `.done`이 없거나 전체 파일 체크섬이 맞지 않는 미완료 파일은 복구 후보가 되지 않는다. 정상 세대가 먼저 지워지지 않는다.
- **증거:** 중단 시점, 전후 파일 목록, 복구 후보 목록.

### B3. 복구 취소와 잘못된 백업 거부

- [ ] **절차:** 현재 기준 데이터를 캡처한다. `백업에서 복구`로 정상 사본을 선택한 뒤 교체 확인에서 취소한다. 이어서 별도 폴더의 **복사본만** 사용해 아래 변형을 각각 확인한다.

| 용량 초과 | 별도 사본을 64MiB 초과로 준비 | 정상 복구 후보로 사용되지 않음. 현재 DB 유지 |
| 틀린 PIN·복구 코드 | 재설치 후 복구에서 맞지 않는 값을 입력 | `PIN 또는 복구 코드가 맞지 않습니다`로 거부, 입력창 재표시. 현재 DB 유지(에뮬레이터 확인) |
| 암호문 변조 | `data`의 일부 문자를 바꾸고 `.done`을 다시 계산 | 복호화 실패로 거부. 현재 DB 유지 |
| 이 설치의 키가 아닌 백업 | 재설치 전 설치의 백업 선택 | 비밀 입력창이 뜬다(에뮬레이터 확인) |

- **주의(암호화 이후):** 복호화한 스냅샷 안에서 payload는 JSON 문자열 안의 JSON이다. 내부 검증을 확인하려면 수정 후 payload UTF-8 SHA-256을 봉투의 `sha256`에 넣고, 저장한 전체 파일 SHA-256을 `.done`에 넣어야 한다. 이를 하지 않으면 단순 체크섬 거부만 확인한 것이다.
- **증거:** 각 변형 이름·결과·오류, 확인 전후 기준값. 변형 제작이 어려운 세부 항목은 `미실행`으로 남긴다.

### B4. 앱 제거·재설치·전체 복구 — OpenSpec 4.2 핵심

- [ ] **절차:** A·B에 정상 백업을 완료하고 기준표·파일을 확보한다. 앱을 OS에서 제거한다. 파일 관리자로 공용 백업과 내보낸 PDF·CSV·JSON이 남았는지 확인한다. 동일 APK를 재설치하고 **새 관리자 PIN을 설정한 뒤(옛 PIN과 달라도 된다)** 관리자 잠금을 해제하고 `백업에서 복구`로 폴더 B를 다시 선택·승인한다. 교체 확인을 승인하면 비밀 입력창이 뜬다. **백업을 만들 때의 PIN 또는 복구 코드**를 입력한다.
- **기대:** 앱 제거 후 공용 파일은 남는다. 재설치한 앱이 예전 접근 권한을 가진 것처럼 동작하지 않는다. 명시적 승인 후 기록을 전체 교체하며 기존·데모 데이터와 중복 병합하지 않는다. 복구 완료 후 기준표 값이 일치한다. 이 기기 키로 열리지 않는 백업은 비밀 없이 복구되지 않고, 틀린 비밀은 거부된다. 재설치 직후 자동 백업이 여러 번 돌아도 옛 설치의 백업이 목록에서 사라지지 않는다. 복구 코드로 연 경우도 같은 결과여야 한다. **구분을 위해 재설치 전후 백업 두 세대의 데이터가 달라지게 만들어 둔다(같은 시연 데이터면 어느 세대가 복구됐는지 구별되지 않는다).**
- **증거:** 제거 전/제거 후/재설치 후 폴더, 복구 확인창·비밀 입력창·완료 화면, 기준표.

### B5. 좌표·식별자·원장·앵커 정밀 비교

- [ ] **절차:** B4 전후 완료 백업을 PC에서 PIN(또는 복구 코드)으로 데이터 키를 풀어 복호화한 뒤 `payload.tables`를 JSON으로 펼쳐 비교한다(암호문 상태로는 비교할 수 없다). 행 순서는 표의 기본 키(`id`, `seq`, `k`, `day`) 기준으로 맞춘다. 앱은 정차 상태로 두고 비교용 새 운행·비용을 만들지 않는다.
- **기대:** `place`, `trip`, `expense`, `setting`, `ledger`, `anchor`, `sync_item`의 업무 데이터가 보존된다. 운행 좌표, ID, 원장 순번·payload·해시, 기존 앵커·영수증이 동일하다. 무결성이 정상이며 복구를 이유로 원장을 새로 만들지 않는다.
- **비교 제외:** 봉투 생성 시각·전체 파일명·백업 상태·설치별 폴더 권한·`privacy_ack`는 설치·백업마다 달라질 수 있다. 타임스탬프 전송을 켠 상태라면 새 기관 응답을 별도 기록한다. 차이를 확인 없이 정상으로 넘기지 않는다.
- **증거:** 비교표 또는 PC의 차이 보고서. 화면에 좌표가 보이지 않는다는 이유로 좌표 보존을 통과 처리하지 않는다.

### B6. 삭제된 비용 ID 재사용 방지

- [ ] **절차:** 확인용 비용 X를 새로 만들고 ID를 백업에서 적는다. X를 삭제하고 정상 백업을 만든 뒤 복구한다. 새 비용 Y를 만들고 다음 완료 백업에서 Y의 ID와 원장을 확인한다.
- **기대:** X는 삭제 이력으로 남고 현재 비용 표에는 없다. Y의 ID는 X보다 크며 과거 ID를 재사용하지 않는다. Y 저장 후에도 무결성이 정상이다.
- **증거:** X·Y ID, 관련 원장 줄, `payload.sequences`.

## C. 차량 매각 전체 삭제 — OpenSpec 4.3

B 절의 확인과 증거 확보를 먼저 마친다. 최근 날짜의 기록을 포함해 5년이 지나지 않은 자료로 수행한다. 보존기간 설정 UI 자체는 현재 구현 범위가 아니므로 없는 설정을 찾거나 날짜를 임의로 바꾸지 않는다.

### C0. 차량 밖 저장(전체 삭제의 선행 조건)

- [ ] **절차:** USB·SD 카드 등 분리 가능한 저장소를 연결한다. `차량 데이터 전체 삭제`를 열고 관리자 PIN을 재확인한다. 먼저 `차량 밖 저장 먼저` 안내가 뜨는지 확인한다. 차량 **내부 저장소 폴더**를 먼저 골라 거부되는지 보고, 이어 분리 가능한 저장소의 폴더를 선택한다. 저장이 끝나면 삭제 확인창으로 넘어간다. 저장소를 제거하거나 저장 중에 기록을 바꿔 실패·재저장 요구가 나오는지도 본다.
- **기대:** 저장 전에는 삭제가 열리지 않는다(에뮬레이터 확인). 내부 저장소는 거부된다. 내보내기 파일(PDF·CSV·검증 JSON)과 `popolog-offsite-*-records.json`(암호화된 기록 사본)이 저장소에 생기고, 앱이 다시 읽어 해시를 대조한다. 하나라도 어긋나면 삭제를 열지 않는다. 저장 후 기록이 바뀌면 다시 저장해야 한다. 안내에 `출장명령서 등 외부 증빙은 사업장에서 별도로 보관` 문구가 보인다.
- **증거:** 안내 화면, 선택 폴더 종류, 저장된 파일 목록, 거부·실패 화면. 폴더 선택기가 스텁이면 `환경 제약`으로 기록한다(이 항목의 저장·검증은 에뮬레이터에서 미실행).

### C1. 취소·정확한 확인 문구

- [ ] **절차:** 설정 마지막의 `차량 매각 전 데이터 정리 → 차량 데이터 전체 삭제`를 연다. 첫 안내에서 닫는다. 다시 열어 `계속`을 누르고 빈칸·`삭재`·`삭제 `를 입력해 본다. 마지막에도 닫는다.
- **기대:** 안내에 차량과 삭제 범위·복구 불가가 표시된다. 정확한 `삭제` 외에는 최종 실행 버튼이 활성화되지 않는다. 취소한 경우 DB·백업·내보낸 파일이 그대로 남는다.
- **증거:** 안내·최종 확인·비활성 버튼, 취소 후 파일 목록.

### C2. 폴더 접근 미승인과 재시작

- [ ] **절차:** 최종 문구를 정확히 입력하고 실행한다. `Download/Popolog` 직접 접근이 아직 승인되지 않은 조건 또는 이전 설치 폴더의 접근이 없는 조건에서 결과를 확인한다. 미완료 상태로 앱을 종료·재실행한다.
- **기대:** 이전 설치의 파일이 제한된 조회에서 안 보인다고 전체 삭제 성공으로 표시하지 않는다. 미완료 안내와 `삭제 대상 폴더 선택`·`전체 삭제 재시도`가 나온다. 사전 접근 확인 실패 단계에서는 백업을 먼저 지우지 않는다. 재실행해도 일반 기록·복구가 재개되지 않는다.
- **증거:** 오류·누락 폴더, 재실행 화면, 남은 파일 목록.

### C3. 재승인·부분 실패·중단 후 재시도

- [ ] **절차:** 미완료 화면에서 요청된 A·B와 `Download/Popolog`를 각각 선택·승인하고 재시도한다. 폴더가 없으면 선택기에서 만든다. 지원 환경에서는 파일 삭제 중 저장소 분리/권한 철회 또는 강제 종료로 중단한 뒤, 저장소·권한을 복원하고 재실행·재시도한다.
- **기대:** 삭제하지 못한 항목이 있으면 미완료로 유지된다. 재시도 시 이미 삭제된 파일 때문에 영구 실패하지 않는다. 중단 후에도 남은 관리 파일을 이어서 제거하며 완료 전에 기록·백업을 재생성하지 않는다.
- **증거:** 중단·실패 시점, 실패 항목, 복원·재시도 결과. 부분 삭제 시점을 잡지 못하면 이 부분은 `미실행`이다.

### C4. 모든 관리 사본 삭제·관계없는 파일 보존

- [ ] **절차:** 전체 삭제를 정상 완료한다. 파일 관리자로 A·B와 `Download/Popolog`를 직접 확인한다. 디버그 빌드라면 Android Studio Device Explorer 등으로 해당 앱 사용자 영역도 확인한다.
- **기대:** 최근 기록을 포함한 운행·비용·장소·운전자·설정·원장·앵커·연동 대기 자료가 제거된다. DB 암호 키와 백업 유도 키도 폐기되어 새 사용을 시작하면 새 키가 만들어진다. C0에서 차량 밖에 저장한 사본은 **삭제되지 않고 남는다**. 관리 백업의 최신·이전·임시 `.json`/`.done`, PDF·CSV·검증 JSON, 앱 내부/앱 전용 외부 파일·캐시가 제거된다. A에 남긴 이전 사본도 없어야 한다.
- **대조군:** `사용자메모.txt`와 관리 폴더 밖에 의도적으로 둔 공유·복사본은 남는다. 앱이 공유 사본까지 삭제했다고 표시하면 안 된다. 내용 없는 매각 완료 상태와 빈 DB 구조는 재기록 방지용으로 남을 수 있다.
- **증거:** 모든 관리 폴더의 전후 목록, 대조군 파일, 완료 화면. 앱 내부 저장소를 확인할 수 없으면 외부 파일 확인과 내부 확인을 나눠 기록한다.

### C5. 삭제 후 기록 재생성 방지·새 사용 시작

- [ ] **절차:** 삭제 완료 후 앱을 종료·재실행하고 기기도 재부팅한다. `새 차량 사용 시작`을 누르기 전까지 일반 기록 화면이나 시연·운전자 조작을 시도한다. 이후 명시적으로 새 사용을 시작한다.
- **기대:** 완료 상태가 유지되고 기존 기록·옛 백업이 자동 복구되지 않는다. 시연·운전자·차량 신호로 삭제된 데이터가 다시 써지지 않는다. 명시적으로 새 사용을 시작한 뒤에만 기록을 시작한다. 데모는 이 시점에 예시 데이터가 다시 생길 수 있으며, 이전 백업을 자동 복구한 것과 구분한다.
- **증거:** 재실행·재부팅 후 화면과 폴더, 새 사용 시작 전후.

| P8 | 실제 모드·타임스탬프 기관 연결 | 전송 켜기 상태에서 하루 마감, 네트워크 차단 후 재실행, 연결 복원 후 재요청 | 기관 응답·대기·재시도와 원장 검증 결과 기록. 끄기 상태에서 새 요청이 시작되지 않는지도 확인 |
| P9 | 실제 모드의 정비 알림 | 확인용 주기를 설정하고 해당 거리 조건에서 정차·정비 비용 입력 | 정차 중 항목별 알림과 정비 입력 연결, 정비 후 재알림 여부 확인 |

### 기능 부재·설정 의존 항목

다음은 실기기 확인만으로 완료할 수 없으므로 준비 없이 통과/실패를 매기지 않는다.

- 관리자 계정 지정·인증·계정 전환 권한: Pleos 계정 API 연동과 정책이 아직 미완료다. 지금의 삭제 확인 문구는 인증이 아니다.
- 실제 외부 비용 자동 연동: 실제 소스가 없다. 데모 샘플의 승인·거절·병합 성공을 실서비스 연동 성공으로 기록하지 않는다.
- PDF QR 웹 검증: 기존 메모에는 검증 주소가 미게시로 기록되어 있다. 게시·접근 가능 여부를 확인한 뒤 별도 수행한다. 앱 내부 검증과 웹 주소 접근 성공을 구분한다.
- 보존기간 만료 알림·기간별 삭제·관리자 기간 변경: 정책은 정해졌지만 이번 백업 변경의 구현 범위가 아니다. 보존 기산점도 미결정이다.
- PDF 관련비용 명세서·법인의 비역년 사업연도 등 기존 미반영 항목은 제품 결정·구현 후 별도 사례를 추가한다.

## 확인 후 처리

- B4·B5의 복구 결과와 해당 실패·중단 사례 증거를 검토해 OpenSpec `4.2` 완료 여부를 판단한다.
- C1~C5의 결과와 삭제 전후 증거를 검토해 OpenSpec `4.3` 완료 여부를 판단한다. 미실행 세부 사례는 명시적으로 남긴다.
- 실패한 항목은 재현 기록을 기준으로 수정하고 해당 경로를 다시 확인한다. 문서 작성이나 화면 촬영만으로 미확인 항목을 완료 처리하지 않는다.
- 결과를 `popolog-team/PROJECT_PROGRESS.md`와 변경안 `tasks.md`에 반영한다. 실제 확인이 끝난 뒤 최종 검토·Archive를 진행한다.
- 이후 새로 발견하는 실기기 확인 항목도 이 문서에 ID·환경·절차·기대 결과를 추가해 한곳에서 관리한다.
